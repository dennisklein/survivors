Transport Survivors

A single-player survivors game for the browser. You drive a train. The train lays its own track as it goes. Wagons are weapons. Hordes come in from every side. Stay alive for ten minutes and beat the boss.

Decisions to approve

This document uses the defaults below. Say OK to approve them all, or name the number to change.

  1. Steering: the train lays track automatically where it drives. You only choose left, straight or right at each tile. There is no separate build mode.
  2. View: top-down square tiles for the MVP. The OpenTTD isometric view comes later.
  3. Run: 10 minutes, then a boss (the Large UFO). Kill it to win.
  4. Self-collision: when the locomotive hits its own wagon, the train takes damage and stops for 1 second. It does not die.
  5. Engine: macroquad, with all game rules in a separate pure-Rust crate that has unit tests.
  6. Art: original programmer art. No OpenTTD or OpenGFX assets (they are GPL-2.0).

1

Core loop

The loop is the same as in other survivors games. Weapons fire automatically. The player only moves. The difference is how the player moves: on rails, on a grid, with a train that gets longer when it gets stronger.

Win and lose

  • The whole train shares one HP pool (start: 100 HP).
  • At 0 HP the run ends: "Train crashed".
  • At 10:00 the Large UFO arrives. Kill it to win.

One run

  • Fixed map, 64 × 64 tiles, random seed per run.
  • No meta progression in the MVP.
  • Expected: 25 to 35 level-ups per winning run.
2

Train and track

This is the part that makes the game different. The rules come from OpenTTD: square tiles, track pieces that connect tile edges, trains that follow the pieces exactly. The survivors genre adds one change: the player does not build first and drive later. The locomotive builds as it drives.

Track pieces

Each tile stores its track as 6 bits, one bit per piece. This is the same idea as OpenTTD's TrackBits. A tile with more than one bit is a junction or a crossing.

Steering rule

The locomotive always moves forward. When it enters a new tile, the game reads the turn key that is held at that moment and picks the exit edge. A ghost arrow on the next tile shows the exit before the train commits to it.

How wagons follow the locomotive

The locomotive keeps a trail: the list of track pieces it drove over, newest first. Its position is one number, s, the distance it travelled. Wagon i is at distance s − i·g on the same trail, with gap g = 0.9 tiles. The game finds the piece that contains that distance and computes the point on the straight line or the arc. So wagons always stay on the rails, also on curves and junctions. The trail drops pieces that are behind the last wagon. To reverse, the game flips the trail.

Enemies and waves

The enemies come from the OpenTTD world. Angry residents do not like your noise. A rival company sends its buses. The UFO disasters from OpenTTD hunt your train. Enemies move freely over the map. They do not need track.

Wagons and upgrades

Wagons are the weapons. The locomotive pulls up to 5 of them. Engine upgrades are the passive items. Each level-up shows 3 random cards from the pool: a new wagon (if a slot is free), a level for a wagon you have, or a level for an engine upgrade. Every item has 5 levels. When everything is at level 5, the card is "Repair: +30 HP".

The coal hopper connects the weapon system to the track system. It turns your rails into a damage zone. A tight loop with two hoppers becomes a ring of fire. This is the kind of synergy that only a train game can have.

XP: each crate holds the XP value of its enemy (see the enemy table). Level n needs 5 + 4·n XP. The first level-up comes after about 5 kills. The game pauses while the cards show.

Later idea: OpenTTD eras as evolutions. A level-5 wagon plus a level-5 upgrade changes the locomotive from steam to diesel, electric, monorail and maglev.

Architecture

One simulation step

The simulation runs at a fixed 60 steps per second. The render loop runs as fast as the browser allows and does at most 5 steps per frame, so a slow frame does not freeze the game. Each step does these operations in this order:

  1. Read input. Latch the turn key for the next tile.
  2. Move the train. Pick exits, build track, update the trail, detect self-collision.
  3. Spawn director: add enemies up to the cap for the current minute.
  4. Move enemies: seek the nearest car, plus separation from neighbours (spatial hash).
  5. Fire weapons whose cooldown is done. Move projectiles. Tick coal fires.
  6. Resolve hits and touch damage. Remove dead enemies and drop crates.
  7. Pull crates in the pickup radius. Add XP. If a level is reached, change the state to LevelUp and roll 3 cards.

Budgets

  • 500 enemies and 300 shots at 60 fps in a browser on a normal laptop.
  • Release wasm under 2 MB.
  • Plain Vec plus swap_remove. No ECS.
  • Spatial hash with one bucket per tile for enemy neighbours and hits.

Tests in sim

  • Track bits: connect, junction, crossing.
  • Trail: car positions on straights and curves, trail trim, reverse.
  • Speed: build speed versus existing track.
  • Same seed gives the same run (determinism).
  • Card pool: no maxed items, no wagon when slots are full.

Toolchain and tasks

mise installs every tool and runs every task. A new contributor runs mise install and then mise run serve. Nothing else is necessary. Exact tool versions get pinned in the first scaffold commit.

# mise.toml
[tools]
rust = { version = "1.99", targets = "wasm32-unknown-unknown", components = "clippy,rustfmt" }
miniserve = "<pin>"      # static file server for dist/
watchexec = "<pin>"      # used by `mise watch`

[tasks.run]
description = "Run the game natively"
run = "cargo run -p game"

[tasks.test]
run = "cargo test --workspace"

[tasks.fmt]
run = "cargo fmt --all"

[tasks.lint]
run = ["cargo fmt --all --check", "cargo clippy --workspace --all-targets -- -D warnings"]

[tasks."build:web"]
description = "Build the wasm bundle into dist/"
sources = ["crates/**/*.rs", "Cargo.*", "web/*"]
outputs = ["dist/game.wasm"]
run = [
  "cargo build -p game --release --target wasm32-unknown-unknown",
  "mkdir -p dist",
  "cp target/wasm32-unknown-unknown/release/game.wasm web/index.html web/mq_js_bundle.js dist/",
]

[tasks.serve]
depends = ["build:web"]
run = "miniserve --index index.html dist"

[tasks.dev]
description = "Rebuild on change (run `serve` in a second terminal)"
run = "mise watch build:web"

[tasks.ci]
depends = ["lint", "test", "build:web"]

MVP scope and commit plan

In the MVP

  • 64 × 64 map with grass, lakes and a map edge.
  • Auto-built track, turns, junctions, crossings, reverse.
  • Locomotive and up to 5 wagons on one trail.
  • 3 wagons, 4 engine upgrades, level-up cards.
  • Residents, buses, Small UFO, Large UFO boss.
  • HUD and all six screens.
  • Native and browser builds through mise.
  • Unit tests for the sim crate.

After the MVP

  • Isometric view and sprites.
  • Sound and music.
  • Touch controls.
  • Stations, money and a shop between runs.
  • Saboteurs, zeppelins, subsidence.
  • Era evolutions, more wagons.
  • High score in local storage.
  • CI and GitHub Pages deploy.

The build thread commits on main, one logical step per commit, with Conventional Commits. The game is playable after commit 4. This lets us test the steering feel early, which is the biggest risk.
